# Runtime Plan 子任务执行摘要设计

## 意图

缓存审批要求用户决定是否复用先前成功的 Plan 子任务。当前界面只展示历史输出、来源 Turn 和完成时间，没有说明任务当时调用了哪些工具、是否产生副作用、是否经过人工确认。执行摘要让用户能评估复用与重新执行的风险。

## 目标与非目标

- 成功子任务记录并展示实际成功调用的工具 ID、调用次数、效果等级，以及该任务发生和通过的人工工具确认次数。
- “复用并跳过”明确表示不会再次调用摘要中的工具；“忽略并执行”明确提示可能重复其副作用，之后仍受现有工具策略和逐工具确认保护。
- 摘要不保存工具参数、工具输出、凭证、幂等键或补偿令牌；原始任务输出仍只在审批请求中展示，不写 Trace。
- 旧数据库记录没有摘要时显示“执行摘要不可用”，不猜测只读/副作用等级，不阻止用户作出明确选择。
- 不建立新的风险审批体系，不改变工具 Policy、已有高影响确认、缓存指纹或缓存匹配范围。

## 方案

1. **在成功结果记录中持久化安全执行摘要（选用）**：Task Executor 收集成功调用的工具 ID 与效果等级，并观察任务期间的确认 Provider 决定；TaskStore 将摘要与成功结果原子保存。审批 UI 和 Trace 展示摘要。旧 schema 迁移后摘要列允许为空。
2. **审批时从 Trace 反查摘要**：避免结果 schema 扩展，但会让审批依赖 Trace retention、span 关联和查询可用性；当前 Trace 只记录计数，无法可靠恢复每个工具和效果等级。
3. **只展示副作用计数**：实现最简单，但无法让用户看出副作用来自哪些工具，也无法确认人工确认情况，信息不足以支撑用户判断。

## 数据与行为

- 执行摘要按工具 ID 聚合：工具 ID、成功调用次数和效果等级。无法从执行适配器确定等级的工具显示为“未知”，不推断为只读。
- 摘要另记录确认请求数与批准数；不包含确认摘要、参数或用户身份。成功任务中零次确认显示“未触发人工确认”。
- 新字段以 JSON 存在 `runtime_plan_task_results`，与 TaskRun 成功状态和输出在同一事务内提交；旧结果迁移后的字段为 `NULL`。
- Trace 的 `plan.task` 完成事件只增加去敏的工具 ID、效果等级和确认计数，不增加参数或输出正文。
- 审批卡片显示：历史执行摘要、历史输出，以及“复用不会再次调用这些工具；重新执行可能重复副作用”的说明。旧记录显示摘要缺失提示。

## 架构位置

摘要由 `GovernedPlanTaskExecutor` 从实际工具调用得到，通过 `PlanTaskResult` 和 `TaskRunHandle` 传到 `CompletedPlanTaskResult`，由 SQLite `TaskStore` 持久化。`WebSocketTaskCacheApprovalProvider` 将摘要传给 `ChatPanel`；Orchestrator 同步把允许列表内的摘要字段写入 Plan Task Trace。

## 验收

- 两个或更多不同工具的成功调用被准确聚合；只读和各副作用等级展示正确，确认次数正确。
- 缓存审批 WebSocket 携带摘要；复用与执行两条选择都显示不同且准确的重复执行说明。
- 旧结果 schema 自动迁移，旧记录摘要为空时 UI 显示未知状态，仍按人工选择执行。
- 摘要与成功结果原子保存；Trace 和数据库摘要不包含原始参数、输出、凭证、幂等键或补偿令牌。
- 现有审批、任务缓存、失败摘要、Trace、前端测试及全量 Python/前端验证通过。
