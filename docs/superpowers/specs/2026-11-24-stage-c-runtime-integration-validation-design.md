# Stage C Runtime 集成验证设计

## 意图

补齐 Runtime Chat 的 Stage C 验证：现有单元测试已覆盖 Skill 格式适配、Plan 兜底和工具候选检索，但需要更稳定地证明这些组件经 Chat 请求入口协作时仍遵守同一请求上下文、预算和工具治理边界。真实模型评测用于观察路由和 Plan 生成质量，不替代确定性自动化测试。

## 目标

- 增加可重复的 Chat/API 集成验证，覆盖已选择 Skill 的执行、执行失败转 Plan、任务级工具检索和工具调用治理。
- 使用 fake Model Provider、隔离 Skill 注册表及内存工具替身；验证拒绝/审批边界时不得触碰真实文件或外部服务。
- 复用现有 Stage C 真实模型评测脚本；完成自动化验证后提供本机手动运行命令，不在自动质量脚本中发送真实模型请求。
- 记录实际覆盖路径、测试结果和未覆盖的模型质量边界。

## 非目标

- 不改变 Runtime、SkillEngine、Plan、Policy Engine 或 Tool Executor 的生产契约，除非新增集成测试揭示具体缺陷。
- 不实现 `builtin.deepagents` 私有状态跨 Host 恢复，不改变其已记录的兼容边界。
- 不调用外部模型、不读取或记录 API Key、不执行真实副作用。
- 不调整路由阈值、评测期望标签或生产工具权限。

## 考虑过的方案

1. **只运行真实模型评测。**最接近实际模型质量，但耗时和结果波动较大，也难以稳定定位运行链路回归。
2. **只增加确定性集成测试。**能稳定验证 Runtime 和治理契约，但不能证明真实模型会正确选择 Skill 或生成 Plan。
3. **先补确定性集成测试，再由用户手动运行现有真实模型场景（选定）。**自动测试提供可重复的契约证据；手动评测单独报告模型决策与 Token/延迟，不把密钥或模型输出写入仓库。

## 范围与约束

- 先核对 `tests/integration` 中已有 Chat、Skill、Plan 用例，避免重复覆盖；新增测试从当前 Chat/API 入口进入，使用仓库现有 Runtime 装配和服务替身。
- 重点验证 YAML/Markdown 入口边界、失败后的 Plan 接棒及候选/失败原因传递、任务级工具候选受授权目录约束、同一个 RequestContext/预算贯穿调用，以及工具执行仍走 ToolFacade/Policy/确认路径。
- 自动化测试必须对真实文件系统和外部工具保持无副作用；需要写入时使用内存 stub，并断言实际 handler 未被调用或只记录到 stub。
- 真实模型步骤复用 `scripts/evaluate_stage_c_runtime.py` 的单用例运行方式，由用户在本机进程配置密钥后执行；报告只记录非敏感模型标识、用量、耗时、路由/Plan 结果及安全断言。
- 以 `docs/stage-c-model-evaluation.md` 为模型评测口径；以 `docs/roadmap.md` 和 ADR-0034 为 Runtime 边界依据。

## 验收

- 新增的自动化集成测试能在没有网络、模型密钥或真实工具服务的环境中确定性运行。
- 测试失败能指出具体链路边界，而不仅是验证内部 mock 被调用。
- 全量 Python 质量脚本通过；测试报告和路线图准确区分自动化契约验证与真实模型质量验证。
- 真实模型评测命令由用户手动执行；在没有本机结果前不声称模型质量已通过。
