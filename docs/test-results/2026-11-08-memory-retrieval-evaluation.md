# Memory Retrieval 离线基线评测

## 范围

- 数据：`docs/evaluations/memory-retrieval-v1.yaml` 中 9 个合成查询，覆盖会话内事实、跨会话隔离、凭证生命周期、工作区权限、沙箱级别、Skill 执行方式、回答偏好和同义改写。
- 对比：当前固定顺序召回模拟，与段落级候选上的本地 BM25 风格词项排序。
- 预算：每次召回最多 220 字符；指标为 Recall@budget、MRR@budget 和平均返回 chunk 数。
- 可复现命令：`.venv/bin/python scripts/evaluate_memory_retrieval.py --char-budget 220`。
- 所有数据均为合成内容；没有调用模型、读取用户记忆文件或修改持久记忆。

## 结果

| 方法 | Recall@budget | MRR@budget | 平均返回 chunk |
| :--- | ---: | ---: | ---: |
| 固定顺序基线 | 66.7% | 0.291 | 5.00 |
| BM25 风格词项排序 | 88.9% | 0.722 | 1.89 |

词项排序在本合成集里更常把目标记忆排在预算范围内，也减少了平均注入的无关片段。对“之前授权的访问口令退出程序后还能用吗？”这条同义改写，词项排序没有命中；固定顺序方法因返回较多内容而覆盖目标，但排序位置靠后。

评测同时校验：当前会话可召回自己的摘要；其他会话的私有摘要不进入候选；相关性标注不能引用其他会话条目；两种策略输出均受字符预算约束。既有 MemoryController Trace 测试继续验证查询和记忆正文不会进入 Trace。

## 结论与边界

- 本地词项排序已作为混合召回的优先排序信号；本报告只评估“命中项排序”，不评估未命中片段的顺序回退。结果来自少量合成数据，不足以作为生产效果承诺。
- 同义改写案例显示词项匹配有已知召回缺口，值得继续评估 Embedding 检索。
- 项目目前没有统一 Embedding Provider 契约，因此本轮无法比较真实语义向量。建议下一步以可选 Embedding Provider 与内存余弦相似度做隔离评测；样例和真实使用场景达到质量门槛前，不引入向量数据库依赖。
- 评测不采集真实记忆语料，未对真实用户数据做质量估算。
