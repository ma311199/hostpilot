# 模块职责边界（当前实现）

本文记录当前实现的模块职责和不可越过的治理边界。总体架构以[新架构文档](新架构文档.md)为准，具体执行决策以[ADR-0029](decisions/0029-three-skill-pipelines.md)、[ADR-0012](decisions/0012-business-skill-fast-path-and-plan-fallback.md)和[ADR-0009](decisions/0009-skill-runtime-and-yaml-contract.md)为准。

这里要区分两个阶段：**Planner 只负责生成任务计划或说明执行前需要用户补充的信息，不选择可执行 ID；执行阶段的 Task Executor 才从已授权候选中选择 Skill 或检索工具。**工具任务由受限 ReAct 子 Agent 执行，业务 Skill 任务直接交给 Skill Runtime，不把两者混为一个通用执行器。

顶层路由的业务 Skill 快速路径还受完整目标覆盖约束：Selector 的置信度和模型 `covers_full_request` 声明都不能单独证明请求已完成。Selector 已加入显式连接多动作时转 Plan 的保守检查；`plan-004` 真实模型复测已验证该请求进入具体澄清，无工具调用和副作用。Skill Runtime 的通用完整目标覆盖能力仍需用更多样例评估，见[plan-004 记录](test-results/2026-11-16-stage-c-plan-004-runtime.md)。

## 问题处理

- **Plan/Planner层**：做**任务分解**和**依赖关系描述**；若必需用户信息缺失，可返回具体澄清问题且不创建执行任务；
- **Orchestrator**：按依赖调度任务并把任务交给 Task Executor；
- **Task Executor**：业务 Skill 任务选择授权 Skill，工具任务检索有界工具并创建受限 ReAct 子 Agent；
- **工具子Agent**：只在单个 `tool_task` 内选择和调用已检索的工具。

这意味着 Planner **不负责选择具体的 tool_id 或 skill_id**。它的核心质量问题是：**子任务拆得对不对——粒度是否合适、有没有冗余、依赖是否正确、每个子任务是否有明确可验证的产出**。执行阶段仍需由 Task Executor 根据任务类型，从当前请求的授权候选中选择能力并再次校验。

“2个子任务能解决却拆成3个”是典型的**过度分解**，它带来的代价是：多创建子Agent、多一轮调度、多一次上下文装配、延迟和成本上升，还可能引入冗余步骤之间的不一致。

### Plan为什么会过度分解

Planner过度分解通常来自四个原因：

1. **不知道能力边界**：Plan层看不到具体tool/skill细节，不知道“一个skill一次能覆盖多大范围”，于是倾向于把步骤拆细。
2. **把“步骤”当“子任务”**：一个skill内部的步骤（如“查询→校验→执行”）被拆成多个子任务，实际上它们应该由一个子Agent调用一个skill完成。
3. **缺少粒度约束和示例**：Prompt里没有告诉Planner“什么算一个子任务”“简单任务最多拆几个”，模型自然倾向“多拆显得完整”。
4. **缺少分解后自检**：没有机制检查“第3个子任务是否必要、是否可合并”。

### 怎么做好分解：六个可落地手段

#### 1. 给Plan层“能力目录”，而不是全量tool schema

Plan层不需要知道每个tool的参数细节，但需要知道**能力单元**：

```yaml
capability_catalog:
  - skill_id: order_query
    capability: "查询单个/多个订单的状态、金额、物流信息"
    coverage: "一次可处理多个订单号"
    output: "结构化订单状态"
  - skill_id: refund_apply
    capability: "对已发货订单发起退款"
    precondition: "订单状态为已发货"
    output: "退款单号"
```

**关键**：能力目录要写清“一次能处理什么范围”。如果`order_query`声明“一次可处理多个订单号”，Planner就不会把“查订单A”和“查订单B”拆成两个子任务。能力目录是Plan层做粒度判断的主要依据。

#### 2. 明确“子任务”的定义和粒度原则

在Planner的system prompt里写死粒度规则：

- **一个子任务 = 一个可独立完成、有明确可验证产出的工作单元**；
- **子任务应尽量与能力目录中的能力单元对齐**：一个子任务尽量由一个skill或一组紧密相关的tool完成；
- **不要把同一skill内部的步骤拆成多个子任务**；
- **不要创建没有独立产出的“中间判断”子任务**：判断逻辑应放在子Agent内部或依赖关系里；
- **能合并的合并**：如果两个子任务无强依赖、产出可合并，应合并为一个。

举例说明：

| 用户问题                  | 正确分解                             | 过度分解                      | 问题                             |
| :------------------------ | :----------------------------------- | :---------------------------- | :------------------------------- |
| 查订单A状态，已发货则退款 | ①查询订单状态 ②条件退款              | ①查状态 ②判断是否已发货 ③退款 | ②是①的产出判断，不应单独成任务   |
| 对比订单A和B金额          | ①查询并对比（一个skill可查多个订单） | ①查A ②查B ③对比               | 不知道能力边界，把能力内步骤拆开 |

#### 3. 用Few-shot示例校准粒度

给Planner的Prompt里放**正例和反例**：

- 正例：简单问题→1~2个子任务；中等→2~4个；复杂→4~6个；
- 反例：简单问题拆成5个、把skill内部步骤拆成子任务、创建无产出的判断任务。

示例要覆盖你业务中高频的“2个子任务解决”的场景，让模型学到“什么时候不该拆”。

#### 4. 前置复杂度评估，约束子任务数量上限

在Plan之前先做一个轻量复杂度判断（规则或小模型）：

- 简单：子任务上限 1~2；
- 中等：上限 3~4；
- 复杂：上限 5~6（可按业务调整）。

把复杂度评估结果和数量上限写进Planner的输入。**这不是硬性截断，而是给Planner一个粒度锚点**，减少“简单问题拆成5步”的倾向。

#### 5. Plan Validator增加“分解质量校验”

Plan Validator除了查依赖环、白名单、预算，还要专门查分解质量：

| 检查项     | 规则                                                         |
| :--------- | :----------------------------------------------------------- |
| 数量合理性 | 子任务数是否超过复杂度对应的上限；超限→提示合并或重规划      |
| 冗余检测   | 两个子任务目标是否高度重叠；重叠→提示合并                    |
| 可合并检测 | 两个子任务无强依赖、产出可合并→提示合并                      |
| 无产出任务 | 是否存在没有明确可验证产出的“中间判断/确认”任务→提示合并到相邻任务 |
| 能力对齐   | 每个子任务是否能对应到能力目录中的能力单元；对不上→可能粒度不对或能力缺失 |
| 必要性     | 去掉某个子任务是否影响最终目标；不影响→可能冗余              |
| 依赖完整性 | 依赖是否覆盖所有真实前置关系，是否有该依赖却没标的           |

**关键原则**：Plan Validator对分解问题**优先提示合并/局部调整，而不是整体重规划**，避免“因为多了一个子任务就全部重来”。

#### 6. 执行中纠偏：Orchestrator/子Agent反馈粒度问题

分解不可能一次完美，执行阶段要有反馈回路：

- Orchestrator发现**多个连续子任务都指向同一个skill/能力**，可能是分解过细，**触发局部合并重规划**；
- 子Agent执行时发现**当前子任务目标过大、无法一次完成**，返回`NEED_SPLIT`标记，触发局部拆分；
- 子Agent发现**当前子任务其实已被前置任务完成**，返回`ALREADY_SATISFIED`，Orchestrator跳过并记录，供后续优化分解；
- 这些反馈进入**分解质量错题集**，用于优化能力目录、Prompt示例和Validator规则。

### 怎么评估分解质量

分解质量必须单独评测，不能只看端到端成功率。

**评测集**：人工标注“正确分解”的样本，每条包含：

- 用户问题；
- 期望子任务数（或范围）；
- 期望子任务目标；
- 期望依赖关系；
- 哪些子任务可合并。

**指标**：

| 指标           | 含义                                          |
| :------------- | :-------------------------------------------- |
| 子任务数量偏差 | Planner输出的子任务数与期望的差值分布         |
| 过度分解率     | 实际子任务数 > 期望上限的样本占比             |
| 分解不足率     | 实际子任务数 < 期望下限、导致子任务过大的占比 |
| 冗余子任务率   | 被人工判定为冗余/可合并的子任务占比           |
| 依赖关系正确率 | 依赖边与人工标注的一致率                      |
| 能力对齐率     | 子任务能对应到能力目录的比例                  |
| 合并建议采纳率 | Validator提示合并后，重规划是否正确合并       |

**重点盯“过度分解率”和“冗余子任务率”**，它们直接对应你说的“2个变3个”问题。

### 落地优先级

| 优先级 | 动作                                                         | 解决什么                          |
| :----- | :----------------------------------------------------------- | :-------------------------------- |
| P0     | 给Plan层提供能力目录（含覆盖范围）                           | Planner知道能力边界，减少无谓拆分 |
| P0     | Prompt写入子任务定义+粒度规则+正反例                         | 校准分解粒度                      |
| P1     | Plan Validator增加分解质量校验（数量/冗余/可合并/无产出）    | 执行前拦截过度分解                |
| P1     | 前置复杂度评估+数量上限                                      | 给粒度锚点                        |
| P2     | Orchestrator/子Agent粒度反馈（NEED_SPLIT/ALREADY_SATISFIED） | 执行中纠偏                        |
| P2     | 建分解质量评测集+指标                                        | 持续度量分解质量                  |
| P3     | 错题集回流优化能力目录和Prompt                               | 长期提升                          |

## Plan Agent职责

#### 当前实现记录（2026-11-15）

- Planner 的计划 Schema 只接收任务目标、执行类型、依赖、任务输入和预期产出；不接收 `tool_id` / `skill_id`。
- Planner 的能力目录只提供能力类型、范围、前置条件和输出描述，不包含可执行 ID 或参数 Schema。
- `tool_task` 在执行阶段按任务目标检索当前授权目录，最多暴露默认 5 个工具给受限 ReAct 子 Agent；子 Agent 可以在同一任务内多轮调用、重复调用同一工具或改用 allowlist 中的其他工具。`business_skill_task` 由 Task Executor 从授权 Skill 候选中选择 Skill ID 和输入，再交给 Skill Runtime；它不经过工具 ReAct 循环。两类任务的最终调用都保留预算、权限、审批和结果校验链。
- 简单/中等/复杂任务粒度建议、少拆优先、能力内部步骤不拆分以及正反例已写入 Planner 指令。
- P1 已增加基于目标长度和并列/顺序线索的复杂度提示（简单 2 项、中等 4 项、复杂 6 项上限）、重复目标检测和预期产出检查；语义冗余/可合并识别仍需后续实现。
- P2 的局部纠偏反馈和 P3 的分解评测仍需后续实现。复杂度估算是轻量规则，后续需要用真实任务评测校准。
- Plan 的五个实现角色已有版本 `1.0` 的显式注册表，可通过配置选择实现；Orchestrator 和治理边界保持核心组件。自定义插件由受信任的 Python 启动代码注册，尚无第三方安装或隔离执行机制。
- 对话框架适配器新增版本 `1.0` 的注册表，默认 `builtin.deepagents`；上层 Skill 路由仍由 HostPilot 负责。
- ModelRuntime 新增版本 `1.0` 的注册表，默认 `builtin.openai-compatible`；替换实现需同时提供统一 ModelProvider 与 Agent 框架适配器。
- 会话元数据使用 `ConversationStore` Port；LangGraph Checkpointer 通过独立异步上下文工厂注入，默认两者仍使用同一个 SQLite 文件。
- 模型非敏感配置和 MCP 连接元数据分别使用专属 Store Protocol/Factory 注入；密钥不进入任一持久化契约。
- Harness 参数、Workspace 路径和 Skill 执行模式偏好也改为独立 Store Protocol/Factory；存储方法按数据域保持明确，不做通用 JSON Store。
- Audit、Cancellation 和 Trace 运行记录分别通过独立 Store Protocol/Factory 注入；自定义实现必须延续各自的数据脱敏、白名单与有界查询约束。
- 会话摘要和长期记忆通过 `MemoryStore` Port 注入；MemoryController 与 MemoryWriteService 继续拥有范围校验、审批、大小限制和统一召回治理。
- 远程 MCP 动态工具路由由独立 `MCPToolRoutingTable` 管理；Provider 仍负责连接生命周期和 Tool Executor 治理。

## 当前执行阶段的职责边界

| 模块 | 当前职责 | 明确不负责 |
| :--- | :--- | :--- |
| `SkillRuntime` | 加载 YAML Skill，检查必填字段和输入/输出 JSON Schema，校验 workflow action、工具依赖和声明风险，执行 DAG，调用准入/结果评估，并返回完成、澄清、Plan fallback 或人工复核状态 | 不负责顶层路由，不授予 Skill 或工具权限，不绕过 Tool Executor |
| `GovernedPlanTaskExecutor` | 执行 `business_skill_task` 和 `tool_task`；为业务任务选择授权 Skill，为工具任务检索有界工具候选并启动受限 ReAct 子 Agent；将预算、上下文、幂等键和确认 Provider 传下去 | 不改变 Policy 决策，不直接执行未经注册的工具，不把完整工具目录交给 Planner |
| 受限 ReAct 子 Agent | 在单个 `tool_task` 内根据目标和结果循环调用已检索的工具，默认最多 5 轮；可重复调用同一工具 | 不能调用检索 allowlist 之外的工具，不能绕过 Tool Executor，也不负责拆分 Plan |
| `ToolExecutor` | 校验工具参数 Schema，执行 Policy/capability 检查，处理高影响操作确认、预算、超时、结果验证、Audit 和 Trace | 不判断业务 Skill 是否适用，不替代 Planner 或 Skill Runtime 的 workflow 校验 |
| `PolicyEngine` 与确认 Provider | PolicyEngine 判断 capability、信任级别和执行环境；高影响工具在 Policy 允许后通过确认 Provider 请求用户批准 | capability 未授予时不会自动向用户申请授权；Skill 声明的 `side_effect_level` 也不等于用户确认 |
| `Orchestrator` | 校验计划、按依赖 wave 调度任务、维护 Blackboard、处理失败/重规划/补偿和最终验证 | 不在 Planner 阶段选择具体 Skill/工具，不直接生成工具参数，不绕过任务执行器 |

### 参数不足、授权和风险的统一口径

- 缺少 Skill `input_schema.required` 字段时，Skill Runtime 在副作用执行前返回 `CLARIFICATION`；Schema 类型或结构错误是输入失败，不自动改写成澄清。
- 准入评估器或结果评估器可以返回 `CLARIFY`、`PLAN` 或 `REJECT`。已有不可逆副作用后再需要澄清时，进入 `HUMAN_REVIEW`。
- Skill/工具 allowlist 和 capability 是系统准入，不是交互式授权。未授权 Skill、未声明依赖或未授予 capability 会被拒绝。
- 高影响工具在 Policy 放行后才请求用户确认；没有确认 Provider、用户拒绝、取消或超时均 fail closed。当前没有“所有高风险 Skill 统一弹一次确认”的 Skill 级确认门。
- Planner/Replanner 可返回不含执行任务的 Plan 级澄清请求；Orchestrator 将其作为 `CLARIFICATION` 终态返回，回退 Adapter 映射为 `clarify` 路由。工具任务未调用工具且 Replanner 判定缺少用户输入时，也可用该终态询问具体缺项。
- 直接执行 Skill 时，Skill Runtime 的澄清问题可直接返回用户。作为 Plan 的 `business_skill_task` 时，底层 Runtime 的澄清状态仍需由 Plan 任务结果显式传递；这一 Skill 子任务澄清传递路径尚未完成验证。

## 项目模块的替换边界盘点

| 模块 | 当前契约/注入点 | 现状 | 后续方向 |
| :--- | :--- | :--- | :--- |
| Plan 组件 | Planner、Validator、Task Executor、Verifier、Replanner Ports | 有版本注册表、实现 ID 配置 | 继续保持 Orchestrator 与治理链稳定 |
| 对话执行框架 | `AgentRuntime` Protocol / `ChatRuntimeRegistry` | 有版本注册表；默认 DeepAgents | 后续可注册其他框架适配器 |
| 路由 | `Router` Protocol、`create_app(agent_router=...)` | 可通过应用依赖注入替换，无独立插件选择配置 | 先稳定路由决策契约和错误行为 |
| 模型提供方 | `ModelProvider` Protocol / `ModelRuntimeRegistry` | 有版本注册表；默认 OpenAI 兼容实现，可替换 Provider 与框架模型适配器组合 | 增加其他 Provider 时仍统一接入预算与 Token 统计 |
| 工具连接 | `ToolInvoker`、`ToolFacade`、MCP transport adapters、`MCPToolRoutingTable` | 连接实现可替换，Facade 统一调用；远程工具路由表独立管理；Server 配置已支持两种传输 | 不让连接插件绕开 ToolFacade、Policy 与审批 |
| 持久化 | 按数据域划分的 Store Ports、Checkpointer Factory、SQLite/Markdown 默认实现 | 会话、配置、运行参数、Workspace、Skill 偏好、审计、取消、Trace、记忆和 Checkpointer 可由代码工厂注入 | 保持数据域契约和安全约束，确有需求时再实现其他后端；不增加通用注册表 |

插件注册表只适用于有稳定契约、需要按部署替换实现的边界；普通内部模块继续使用显式依赖注入即可，避免把所有类都变成插件。

| 模块                | 一句话定位                                         | 是否用LLM                     |
| :------------------ | :------------------------------------------------- | :---------------------------- |
| **Plan（Planner）** | 把顶层目标拆成子任务，描述依赖关系，不选具体tool/skill ID | **必须用LLM**（核心推理）     |
| **Plan Validator**  | 执行前校验计划是否合规、粒度是否合理               | **规则为主，LLM为辅**         |
| **Orchestrator**    | 按依赖图调度子任务、创建子Agent、维护Blackboard    | **基本不用LLM**（纯调度代码） |
| **Blackboard**      | 存储任务状态、结果、依赖快照的共享状态区           | **不用LLM**（数据结构）       |



| 维度                 | Plan                                         | Plan Validator                          | Orchestrator              | Blackboard                         |
| :------------------- | :------------------------------------------- | :-------------------------------------- | :------------------------ | :--------------------------------- |
| **核心职责**         | 任务分解+依赖描述                            | 计划合规与质量校验                      | 调度执行+状态维护         | 状态存储与快照分发                 |
| **输入**             | 顶层目标、约束、能力目录、上下文、复杂度评估 | Plan输出的计划、能力目录、权限/预算约束 | 已校验的计划、子任务状态  | Orchestrator写入的状态、结果、依赖 |
| **输出**             | 子任务清单+依赖图+每个子任务目标             | 通过/不通过+问题清单+修正建议           | 子Agent创建/派发/状态更新 | 只读快照给子Agent/Verifier         |
| **是否写Blackboard** | 否                                           | 否                                      | **是（唯一写者）**        | 被写                               |
| **是否选tool/skill** | **否**                                       | 否（只校验白名单/能力对齐）             | 否                        | 否                                 |
| **LLM使用**          | **必须**                                     | 规则为主，语义冗余/可合并检测可用LLM    | 基本不用                  | 不用                               |



### 1. Plan（Planner）

**职责：**

- 接收顶层目标、约束、能力目录、复杂度评估；
- 输出子任务清单，每个子任务包含：目标、输入、期望产出、依赖关系；
- 标注子任务类型（如 tool_task / business_skill_task / reasoning_task），但**不指定具体tool/skill**；
- 控制粒度：遵守复杂度对应的子任务数量上限，避免过度分解。

**不负责：**

- 不选具体tool/skill ID（由执行阶段的 Task Executor 和工具子 Agent 负责）；
- 不做合规校验（由Plan Validator负责）；
- 不做调度（由Orchestrator负责）；
- 不写Blackboard。

**LLM使用：必须。**
任务分解本质是开放式推理，依赖LLM理解目标、拆解步骤、判断依赖。这是整个链路最需要LLM的环节。能力目录、粒度规则、正反例都通过Prompt注入。

**关键设计：**

- 输入能力目录（写清每个能力单元覆盖范围），让Planner知道能力边界；
- Prompt写死粒度规则+正反例；
- 输入复杂度评估结果和子任务数量上限；
- 输出结构化JSON，子任务和依赖字段强schema。

------

### 2. Plan Validator

**职责：**

- **合规校验**：依赖是否有环、工具/Skill是否白名单、权限是否满足、预算/超时是否超限、必选步骤是否缺失；
- **分解质量校验**：子任务数量是否超上限、是否有冗余子任务、是否有可合并子任务、是否有无产出的“中间判断”任务、每个子任务是否能对齐能力目录；
- **兜底场景校验**：若来自业务Skill升级，检查是否跳过已完成步骤、是否避免重复副作用、是否安排去重/补偿；
- 输出：通过 / 不通过 + 问题清单 + 修正建议（局部合并/局部重规划/整体重规划）。

**不负责：**

- 不重新做分解（由RePlanner/Planner负责）；
- 不调度（由Orchestrator负责）；
- 不校验执行结果（由Verifier负责）。

**LLM使用：规则为主，LLM为辅。**

- **规则可判的**：依赖环、白名单、权限、预算、schema、数量上限、必选步骤缺失、无产出任务检测（如子任务目标为空/只有“判断”动词）——**纯规则**；
- **规则难判的**：语义冗余（两个子任务目标是否高度重叠）、可合并（无强依赖且产出可合并）——**可用LLM做语义判断**，但输出要结构化（冗余/不冗余+理由），且只作为建议，不直接触发整体重规划；
- **原则**：Validator先用规则跑全量，只有规则无法判定的样本才调LLM，控制成本。

**关键设计：**

- 规则校验几乎零成本，应作为第一道闸门；
- LLM只做“语义冗余/可合并”这类规则写不出来的判断；
- Validator不通过时**优先局部合并/局部调整**，避免因多一个子任务就整体重规划。

------

### 3. Orchestrator

**职责：**

- 初始化Blackboard分区（核心区/执行区/归档区）；
- 按依赖图调度子任务：依赖满足则派发，支持并行/串行；
- 根据子任务类型创建对应子Agent或调用Skill Runtime；
- 给子Agent装配输入：System Prompt + 子任务目标 + Blackboard只读快照（仅自身+前置依赖）+ 全局高优记忆 + 私有滑动窗口；
- 接收子Agent返回的结果/错误/副作用记录，**统一写入Blackboard**；
- 跟踪预算消耗、超时、重试、循环检测；
- 子任务失败时按规则决定：重试 / 跳过 / 触发RePlanner / 升级人工；
- 所有子任务完成或终止后，触发Verifier。

**不负责：**

- 不做任务分解（由Planner负责）；
- 不校验计划合规（由Plan Validator负责）；
- 不选具体tool/skill ID；工具任务的候选检索和业务 Skill 的授权选择由 Task Executor 在执行阶段完成；
- 不直接生成最终答案（由Aggregator负责）。

**LLM使用：基本不用。**
Orchestrator是**确定性调度器**，核心逻辑是依赖图遍历、状态机、预算跟踪、超时重试，全部可用代码实现。以下情况可考虑轻量LLM或规则：

- 子任务失败后的“重试/跳过/升级”决策：**优先规则**（错误类型、重试次数、副作用等级、预算），规则无法覆盖的边界情况可升级给RePlanner，而不是Orchestrator自己调LLM；
- 多个子任务结果冲突时的初步判断：**交给Verifier**，不是Orchestrator的职责。

**关键设计：**

- Orchestrator保持“薄而确定”，不承担语义判断；
- 所有需要语义判断的决策（分解、校验、验证、重规划）都交给专门模块；
- Blackboard唯一写者，保证状态一致性。

------

### 4. Blackboard

**职责：**

- 存储结构化的共享状态：核心区（顶层目标、约束）、执行区（子任务状态、结果、错误、副作用记录、预算消耗、幂等键）、归档区（已完成任务的详细记录）；
- 向子Agent提供**只读快照**：仅包含自身+前置依赖任务的相关信息，不是全量黑板；
- 支持`NEED_DETAIL`：子Agent需要明细时，向记忆控制器或归档区拉取原始数据；
- 记录子任务状态流转、结果版本、副作用、幂等键，供Verifier/RePlanner/Aggregator读取。

**不负责：**

- 不做任何决策；
- 不选tool/skill；
- 不生成内容（快照的“精简”由Orchestrator按规则裁剪，或由记忆控制器处理）。

**LLM使用：不用。**
Blackboard是**数据结构+存储**，核心是schema设计、读写权限、版本管理、快照裁剪规则。快照精简可以用规则（按依赖关系裁剪字段），不需要LLM。

**关键设计：**

- **仅Orchestrator可写**，子Agent/Skill Runtime只返回结果，不直接写；
- 快照按依赖裁剪，避免全量黑板污染子Agent上下文；
- 记录副作用和幂等键，供兜底升级和Verifier使用。

# Sub agent职责边界

规划子Agent职责和工具/Skill减压，核心可以统一到一个视角：**控制每个决策点在“动作空间”里需要面对的候选数量**。规划器面对的工具太多，选不准；子Agent拿到的工具太杂，上下文被工具schema撑满；这些本质上是同一个问题在不同层级的表现。可以分**子Agent侧**和**Tool/Skill侧**两条线同时做，再在**Orchestrator调度层**做衔接。

## 子Agent职责规划：用“能力封装”缩小规划器的动作空间

### 🤖 工具任务子 Agent：当前边界与后续封装方向

当前实现只在 Plan 的 `tool_task` 中创建受限 ReAct 子 Agent；`business_skill_task` 直接进入 Skill Runtime。下面的工具集 Agent 化是后续可选的能力封装方向，不改变当前执行入口。

如果规划器每一步都要面对N个叶子工具，选择准确率会随N增长而下降。一个经过生产验证的模式是**Toolset Agentization**：把生产轨迹中频繁共用的工具组，封装成一个子Agent，规划器只调用这个子Agent的单一高层接口，子Agent内部再去编排它拥有的叶子工具。

```
顶层规划器
  ├─ 订单子Agent（内部：查订单、改地址、取消订单）
  ├─ 退款子Agent（内部：验资格、算金额、发起退款）
  └─ 通知子Agent（内部：发短信、发邮件、站内信）
```

规划器的动作空间从N个叶子工具缩小到K个子Agent（K ≪ N），每个子Agent面对的是一个小而集中的本地工具目录，选择准确率显著更高。有研究报告，这种模式带来了**更高的任务成功率、更短的调用轨迹和显著降低的上下文开销**，并在生产环境中实质性地减少了人工验证成本和运营成本。

**子Agent的职责边界应该这样定义：**

- 每个子Agent对应一个**业务能力域**，而不是一组零散工具；
- 子Agent的System Prompt写清**能力边界、前置条件、输出契约**，不写具体工具细节；
- 子Agent内部拥有该能力域内的叶子工具，**工具白名单由Orchestrator在创建时注入**，子Agent不能越权访问其他域的工具；
- 子Agent只向Orchestrator返回**结构化结果**，不直接写Blackboard。

### 🚧 子Agent工具白名单：只给“够用”的工具，不给“全部”

不是每个子Agent都需要所有工具。精简工具列表可以直接减少提示词中的工具定义部分，降低上下文负担。Orchestrator创建子Agent时，应该根据子任务的**能力类型**注入一个**受限工具集**，而不是把全局工具目录全部暴露。

权限也要按子Agent收敛：只读、写入操作不能共用工具白名单，子Agent内部的大量检索和工具调用不应回流污染主Agent或兄弟Agent的上下文。

### 🔒 子Agent上下文隔离 + 结构化摘要返回

子Agent应该运行在**独立的上下文窗口**中，父子上下文分离。子Agent内部的中间推理、工具调用细节属于私有，返回给Orchestrator的只应该是**结构化摘要**，而不是完整的执行日志。

这带来两个减压效果：

1. Orchestrator和Blackboard不会被某个子Agent的大量工具中间结果撑爆；
2. 每类子Agent可以**单独写评测、单独调提示词、单独收敛权限**，故障隔离和调优粒度都更细。

## 🛠️ Tool/Skill侧减压：不要让LLM面对全量工具schema

### 🎯 Tool RAG：检索前置，按需暴露

在工具数量较大的场景下，把全部工具定义直接塞给LLM，基线性能会因上下文过载而坍塌。一个248工具的Kubernetes工具集实验显示，全量暴露的基线端到端准确率只有**12.0%**，而先做检索、只把Top-K候选交给LLM，准确率恢复到**78.0%~82.0%**。

当前工具任务默认检索最多 5 个候选工具；该上限由 Harness 的 `plan_tool_candidate_limit` 管理，允许配置为 1–20。候选数量影响召回和上下文成本，应结合项目评测调整，不能把外部工具集的实验数字当作 HostPilot 的质量保证。

关键区分两个指标：**Gold Tool Recall@K**衡量检索是否把正确工具放进了候选集，**End-to-end Accuracy**衡量最终任务是否成功。**检索召回率必须作为一级监控指标**，因为正确工具没被召回，LLM再强也选不中。

### 🧱 两阶段惰性加载：先给摘要，按需给完整schema

即使做了检索，如果把Top-K工具的完整JSON schema全部注入，每轮的工具token开销仍然可观。**Tool Attention**的做法是：上下文中只保留一个**紧凑的摘要池**，只有被**门控选中**的Top-K工具才**按需提升完整JSON schema**，并用**LRU缓存管理**。在模拟的120工具、6服务器场景中，每轮工具token从47.3k降到2.4k，**减少95.0%**，上下文有效利用率从24%提升到91%。

可以配合**状态感知门控**：在工具暴露之前**先检查前置条件和访问范围**，**不满足条件的工具连摘要都不进上下文**。

### ⚠️ 工具选择存在“相变点”，数量本身就要控制

研究已经识别出，当扁平工具库超过**约60个**时，路由准确率会**出现显著下降**，驱动因素是语义混淆性。这意味着工具/Skill侧减压不能只靠“检索得好”，**工具总数本身需要被治理**：

- 合并功能高度重叠的工具；
- 对语义相近的工具做明确的**判别性描述工程**；
- 如果某些工具总是被一起调用，考虑用**Toolset Agentization**把它们包成一个子Agent，而不是让规划器逐个选。

描述工程是一个**零训练、低成本**的干预手段，可以实质性地扩展Agent的可操作工具容量，但效果**高度依赖模型**：专家级描述对某些模型有帮助，对另一些模型可能降低准确率。因此描述优化必须结合你自己的模型做A/B验证，不能假设“写得更细一定更好”。

## 🔗 Orchestrator在中间做什么

Orchestrator不选工具，也不做任务分解，但它是**减压的执行枢纽**：

```
Plan基于能力目录分解 → 输出子任务(含task_type) →
Task Executor 按任务类型选择授权 Skill 或检索工具 →
tool_task 创建受限 ReAct 子 Agent → 子Agent内部循环调用工具
```

1. **只为工具任务创建子Agent，注入受限工具白名单**：根据子任务的能力域，只给该子Agent够用的工具，而不是全局目录；业务 Skill 任务直接交给 Skill Runtime。
2. **维护工具注册表和能力摘要**：Planner需要的能力目录由Orchestrator或Skill Registry提供，写清“每个能力单元覆盖什么范围”，帮助Planner控制分解粒度，避免把同一能力内的步骤拆成多个子任务。
3. **工具检索的服务化**：如果工具数量大，把Tool RAG做在Orchestrator侧或独立工具检索服务中，子Agent请求工具时先经过检索门控，再拿到Top-K候选和**惰性加载的schema**。
4. **预算和超时跟踪**：工具调用的次数、token、延迟在Orchestrator层统一记账，超限时触发规则决策（重试/跳过/升级），而不是让子Agent各自失控。
